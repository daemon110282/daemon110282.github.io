# Что включать в Constitution

## Analytic

1. Бизнес требования

   - MUST BDD, ATDD

2. Testability & Acceptance Criteria

  Каждое требование MUST быть проверяемым.

  Правила:

  - Каждая User Story MUST содержать критерии приемки.
  - Критерии приемки SHOULD использовать формат Given / When / Then.
  - MUST описывать позитивные и негативные сценарии.
  - MUST учитывать граничные значения и обработку ошибок.
  - MUST обеспечивать трассируемость между требованиями и тестами.
  - Критичные бизнес-процессы MUST покрываться интеграционными тестами.
  - MUST определять критерии завершения реализации (Definition of Done).

3. UX/Accessibility

  - Стандарты доступности (WCAG AA/AAA)
  - Поддержка устройств (mobile-first, responsive)
  - Производительность (Core Web Vitals)

4. Архитектурные принципы

  Стиль архитектуры (Feature-Sliced Design, Clean Architecture, Microservices)
  Паттерны проектирования:

  Архитектурные решения MUST соответствовать согласованной архитектуре системы.

  Правила:

  - MUST соблюдать разделение ответственности между компонентами.
  - MUST минимизировать связанность компонентов (loose coupling).
  - SHOULD использовать существующие сервисы и компоненты до создания новых.
  - MUST документировать изменения публичных контрактов.
  - MUST учитывать обратную совместимость API и интеграций.
  - Архитектурные решения, существенно влияющие на систему, MUST фиксироваться в ADR.
  - MUST определять границы ответственности и владельцев данных.

  Приоритет: простота, сопровождаемость и надёжность выше необоснованной технической сложности.

5. Security и Privacy

  Безопасность MUST учитываться на этапе проектирования требований.

  Правила:

  - Compliance (GDPR, и т.д.)
  - MUST применять принцип минимальных привилегий (Least Privilege).
  - MUST разделять аутентификацию и авторизацию.
  - MUST проверять права доступа на Backend.
  - MUST учитывать защиту персональных и конфиденциальных данных.
  - MUST исключать передачу секретов в исходном коде и логах.
  - MUST определять требования к защите API от несанкционированного доступа.
  - MUST учитывать угрозы из OWASP Top 10 и OWASP API Security Top 10.
  - Для критичных операций MUST определять дополнительные меры защиты.
  - MUST фиксировать требования к аудиту значимых действий пользователя.

6. API-First & Integration Contracts

  Контракты взаимодействия MUST быть определены до реализации интеграций.

  Правила:

  - REST API MUST описываться через OpenAPI.
  - API MUST иметь согласованные правила именования ресурсов и операций.
  - MUST определять форматы запросов и ответов.
  - MUST описывать ошибки, HTTP-коды и бизнес-коды ошибок.
  - MUST предусматривать валидацию входных данных.
  - Для операций изменения состояния MUST оцениваться необходимость идемпотентности.
  - MUST учитывать версионирование и обратную совместимость контрактов.

  Для асинхронных интеграций MUST определять формат сообщений, обработку повторов и ошибок.
